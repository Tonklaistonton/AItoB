# รายงานโครงการและแผนดำเนินงาน AItoB

โครงการ AI ภายในองค์กรเพื่อช่วยงานข้อมูลและงานเอกสาร

ฉบับส่งงาน 20 ตุลาคม 2026 | จัดทำโดยโครงการ AItoB

## บทสรุปโครงการ

AItoB มีแนวคิดให้บริการสำรวจความต้องการ ติดตั้ง และดูแล AI ที่ประมวลผลบนเครื่องขององค์กร โดยเชื่อมโมเดลภาษากับเครื่องมือที่ตรวจสอบสิทธิ์ได้ เป้าหมายคือช่วยงานที่ทำซ้ำ เช่น สรุปข้อมูลค่าใช้จ่าย ค้นและสรุปอีเมล ทำความสะอาดข้อมูล และค้นนโยบายองค์กร พนักงานยังเป็นผู้ตรวจและรับผิดชอบผลลัพธ์ก่อนนำไปใช้งาน

ต้นแบบปัจจุบันใช้ Ollama เรียก Gemma4 รุ่น 12B และใช้ Open WebUI เป็นหน้าจอสนทนา มี Gateway สำหรับยืนยันสิทธิ์และเรียกโมเดล รวมทั้ง Assistant และ MCP tools สำหรับทำงานเฉพาะทาง ส่วนตรวจและรวมยอดค่าใช้จ่ายใช้กฎโปรแกรมกับ Decimal เพื่อคำนวณเงิน ไม่ได้ให้โมเดลภาษาคิดยอดเอง

ผลทดสอบที่มีหลักฐานคือการรับ Excel สังเคราะห์ 6 แถว ผ่าน 3 แถว ซ้ำ 1 แถว ปฏิเสธ 2 แถว รวม 2,000.00 บาท พร้อมดาวน์โหลด CSV และรายงานรายแถว นอกจากนี้มีผลตรวจด่านสิทธิ์ Finance และการป้องกันบัญชี HR เปิดผลลัพธ์ของผู้ใช้อื่น ยังไม่มีผลวัดการลดเวลางานจริง ROI หรือจำนวนผู้ใช้พร้อมกัน จึงนำเสนอประโยชน์เหล่านี้เป็นเป้าหมายของการนำร่อง

## ลูกค้าเป้าหมายและปัญหาที่ต้องการแก้

ลูกค้าของ AItoB คือองค์กรขนาดเล็ก กลาง และใหญ่ที่ต้องการใช้ AI ภายในบริษัทเพื่อเพิ่มประสิทธิภาพและควบคุมค่าใช้จ่าย ขนาดองค์กรอย่างเดียวไม่เพียงพอสำหรับเลือกเครื่องหรือโมเดล ต้องสำรวจจำนวนผู้ใช้พร้อมกัน ปริมาณงาน ขนาดเอกสาร ระดับความลับ และข้อกำหนดของระบบเดิมด้วย

| กระบวนงาน | ปัญหาที่ผู้ใช้โครงการระบุ | แนวทางของ AItoB | สิ่งที่ต้องวัดกับลูกค้า |
| --- | --- | --- | --- |
| สรุปค่าใช้จ่ายรายวัน | ทำซ้ำทุกวันและมีโอกาสคัดลอกหรือรวมยอดผิด | ตรวจข้อมูลและรวมยอดตามกฎ พร้อมรายการที่ไม่ผ่าน | เวลารวม ความถูกต้อง และงานแก้ไขซ้ำ |
| อ่านอีเมล | ใช้เวลาอ่านและจับประเด็นจากหลายฉบับ | ค้นและสรุปเฉพาะข้อความที่มีสิทธิ์ พร้อมแหล่งอ้างอิง | ประเด็นตกหล่น ข้อความที่แต่งเพิ่ม และเวลาคนตรวจ |
| ทำความสะอาดข้อมูล | ต้องใช้สูตรและหลายขั้นตอนก่อนนำข้อมูลไปใช้ | เรียกกระบวนการตรวจผ่านคำสั่งภาษาไทย แล้วรับ CSV และ audit | รายการซ้ำ ข้อมูลผิด และความสามารถไล่กลับแถวต้นทาง |
| ค้นคู่มือองค์กร | พนักงานต้องค้นข้อมูลจากเอกสารหลายแห่ง | ค้นเอกสารตามสิทธิ์และตอบพร้อมรหัสแหล่งข้อมูล | ความถูกต้อง แหล่งอ้างอิง และการไม่เปิดข้อมูลข้ามสิทธิ์ |

ตัวอย่างข้างต้นเป็น pain point จากเจ้าของโครงการ ยังไม่ใช่ผลสำรวจลูกค้าที่ระบุจำนวนองค์กรหรือจำนวนผู้ตอบ แบบธุรกิจจึงต้องเริ่มจากการตรวจความต้องการและ baseline ก่อนเสนอผลตอบแทน

## กระบวนการสำรวจความต้องการลูกค้า

เริ่มจากสัมภาษณ์เจ้าของกระบวนงานและผู้ปฏิบัติงาน ให้ทั้งสองฝ่ายอธิบายจุดเริ่ม จุดสิ้นสุด ข้อมูลนำเข้า ผลลัพธ์ที่ยอมรับได้ และผลกระทบเมื่อทำผิด จากนั้นสังเกตงานจริงและเก็บตัวอย่างที่ได้รับอนุญาต โดยลดข้อมูลส่วนบุคคลที่ไม่จำเป็น

บันทึกจำนวนรายการต่อวัน ความถี่ เวลาที่คนใช้จริง เวลาตรวจแก้ และชนิดข้อผิดพลาด เลือกตัวอย่างทั้งข้อมูลปกติ ข้อมูลผิด ไฟล์ไม่รองรับ และกรณีไม่มีสิทธิ์ เพื่อไม่ให้การทดสอบครอบคลุมเฉพาะงานที่ระบบทำได้ง่าย

จัดลำดับ use case จากประโยชน์ที่คาดหวัง ความพร้อมข้อมูล ความยากในการเชื่อมระบบ และความเสียหายหากผลผิด ก่อนเริ่มพัฒนาต้องตกลงเกณฑ์ตรวจรับ เช่น ยอดตรงทุกกรณีในชุดทดสอบ รายการไม่หาย การอ้างอิงกลับไปยังต้นฉบับ และสิทธิ์ที่ต้องถูกปฏิเสธ

เอกสารส่งมอบช่วงสำรวจควรมีผังกระบวนงานเดิม รายการ pain point ชุดข้อมูลตัวอย่างที่อนุญาต ตาราง baseline ขอบเขตงาน และผู้รับผิดชอบตรวจรับ ยังไม่ควรเริ่มจากการเลือกโมเดลเพียงเพราะมีขนาดใหญ่หรือมีคะแนน benchmark สูง

## ขอบเขตและสถาปัตยกรรมระบบ

ผู้ใช้เข้า Open WebUI แล้วเลือก AItoB Assistant ตัว Pipe รับข้อความและใช้ key รายผู้ใช้ติดต่อ Assistant HTTP bridge ฝั่ง backend ตรวจสิทธิ์จาก key ไม่ใช้ role ที่ผู้ใช้ส่งในข้อความเป็นแหล่งตัดสินสิทธิ์

เส้นทางสนทนาทั่วไปส่งต่อไปยัง agent ซึ่งเรียก Gateway เพื่อให้ Ollama สร้างคำตอบหรือเสนอ tool call จากรายการที่อนุญาต Agent ตรวจชื่อเครื่องมือ พารามิเตอร์ และจำนวนครั้งก่อนเรียก MCP tools ฝั่งเครื่องมือตรวจสิทธิ์ซ้ำก่อนอ่านข้อมูล โมเดลไม่มีอำนาจเพิ่มสิทธิ์ให้ตนเอง

เส้นทางไฟล์แนบค่าใช้จ่ายทำงานแบบกำหนดกฎ เมื่อผู้ใช้สั่งตรวจไฟล์ Pipe ตรวจสิทธิ์ Finance แล้วหาไฟล์จาก record เจ้าของใน Open WebUI ส่ง bytes ไป backend ซึ่งตรวจสิทธิ์ซ้ำก่อน decode และ parse ผลรวม รายงานรายแถว และกราฟสัดส่วนมาจากโปรแกรม เส้นทางนี้ไม่ส่งเนื้อหาให้ LLM ผ่าน AItoB pipeline อย่างไรก็ตาม ระบบอัปโหลดและสกัดข้อความทั่วไปของ Open WebUI เป็นอีกชั้นหนึ่ง จึงไม่อ้างว่าทั้งแพลตฟอร์มไม่มีการอ่านหรือประมวลผลไฟล์ก่อน Pipe

| องค์ประกอบ | ตำแหน่งหรือพอร์ตต้นแบบ | หน้าที่ |
| --- | --- | --- |
| Ollama | Mac localhost 11434 | จัดการและรันโมเดล |
| Gateway | Mac localhost 8000 | ยืนยัน key กรองสิทธิ์ และเรียก inference |
| Gmail backend | พอร์ต host 8001 | ตรวจเจ้าของ mailbox ค้นและอ่าน Gmail |
| Assistant bridge | พอร์ต host 8002 | รับ chat และ API ตรวจหรือส่งออกค่าใช้จ่าย |
| MCP tools | stdio ภายใน container | เครื่องมือเอกสาร อีเมล และ CSV |
| Open WebUI | Mac localhost 3000 | บัญชีผู้ใช้ แชต ไฟล์ และ Pipe |
| SSH tunnel | Windows localhost 3001 ไป Mac 3000 | เข้าเว็บจาก Windows โดยใช้เส้นทาง SSH |

การค้นเอกสารใน source ปัจจุบันใช้ keyword และเอกสารตัวอย่างใน documents.py มีการกรองสิทธิ์ก่อนจัดอันดับ ยังไม่ใช่ระบบ vector database หรือการนำเข้าคลังเอกสารองค์กรเต็มรูปแบบ การเพิ่ม embeddings การเชื่อม ERP และ dashboard บริหารเป็นงานอนาคต

## Ollama และโมเดลที่เลือกใช้

Ollama เป็น runtime และ API สำหรับเรียกโมเดล ส่วน Gemma4:12b เป็นชื่อ tag ของโมเดลที่ติดตั้งบนเครื่อง ทั้งสองเป็นคนละองค์ประกอบกัน ข้อมูลที่เก็บจาก Mac ยืนยัน Ollama 0.40.5 และโมเดล family gemma4_unified ขนาดประมาณ 12.4B parameters ใช้ runner MLX และ quantization nvfp4 ในรูปแบบ safetensors

เหตุผลเชิงออกแบบของการใช้รุ่นนี้คือให้โมเดลทำงานบนเครื่อง Apple Silicon ที่มีอยู่ รองรับการสนทนาและการเรียกเครื่องมือในแนวทาง agent และเชื่อมผ่าน API ภายในได้ แหล่งทางการระบุการใช้งาน Gemma4 ผ่าน Ollama และคุณสมบัติด้าน tool calling [1] เหตุผลเหล่านี้เป็นความเหมาะสมกับต้นแบบ ไม่ใช่ผลสรุปว่าดีกว่าทุกโมเดล เพราะโครงการยังไม่มีการทดลองเปรียบเทียบภาษาไทยแบบควบคุมหลายรุ่น

ข้อมูลโมเดลรายงาน context สูงสุด 262,144 tokens แต่ไม่ใช่ค่าที่ระบบใช้งานทุกคำขอ โค้ด Gateway และเส้นทางสรุปหลายส่วนกำหนด num_ctx เป็น 4,096 และจำกัดผลตอบต่างกันตามงาน การเพิ่ม context ต้องวัดหน่วยความจำและเวลาใหม่ ไม่ใช้ context สูงสุดของโมเดลเป็นคำรับรองความเร็ว

โครงการใช้โมเดลที่ฝึกมาแล้วร่วมกับ system prompt และเครื่องมือ ไม่พบขั้นตอน fine tuning หรือการฝึก weights ใหม่ใน source ที่เก็บมา แม้ metadata โมเดลมี vision และ audio แต่ระบบงานที่ส่งนี้ยังไม่มีผลตรวจรับการใช้งานสองส่วนดังกล่าว

เกณฑ์เลือกโมเดลสำหรับลูกค้าในอนาคตควรมีชุดโจทย์ภาษาไทย ความถูกต้องของ tool call ความตรงกับแหล่งข้อมูล การปฏิเสธเมื่อข้อมูลไม่พอ latency หน่วยความจำ และเงื่อนไขการใช้งาน ทดสอบด้วยข้อมูลเดียวกันและให้คนตรวจคำตอบก่อนเลือก

## Hardware Requirements และเวอร์ชันต้นแบบ

ตารางนี้เป็นเครื่องที่เก็บหลักฐานจริง ไม่ใช่ minimum requirement สำหรับทุกองค์กร ข้อมูลมาจาก Terminal และรายงาน metadata ของ Mac ที่เจ้าของโครงการรันเก็บเมื่อ 20 ตุลาคม 2026 ตามปฏิทินไทย โดยเวลาบางรายการใน JSON เก็บเป็น UTC

| รายการ | ค่าที่ตรวจพบ |
| --- | --- |
| CPU และสถาปัตยกรรม | Apple M5 แบบ arm64 รหัสเครื่อง Mac17,2 |
| RAM | 25,769,803,776 bytes หรือ 24 GiB |
| พื้นที่จัดเก็บที่ระบบรายงาน | รวมประมาณ 994.6 GB ว่างประมาณ 695.3 GB ณ ตอนเก็บข้อมูล |
| ระบบปฏิบัติการ | macOS 27.0.1 build 26A434 |
| Ollama | 0.40.5 |
| โมเดล | gemma4:12b รุ่นที่ติดตั้งแสดงขนาด 7.7 GB และ ID ขึ้นต้น c7597fc90b86 |
| Open WebUI | 0.12.3 พร้อมเก็บ image digest สำหรับติดตั้งอ้างอิง |
| Docker | 29.7.2 |
| Python ใน image ของโครงการ | 3.12.15 |
| MCP ใน image ของโครงการ | 2.3.0 |
| Pipe ของโครงการ | 0.1.3 |

การประเมิน RAM ต้องรวม weights ที่ resident จริง KV cache ตาม context และจำนวนคำขอ ระบบปฏิบัติการ Docker ข้อมูลที่กำลังทำงาน และพื้นที่เผื่อ ขนาดไฟล์โมเดล 7.7 GB จึงไม่ใช่ RAM ทั้งหมดที่ต้องใช้ พื้นที่ดิสก์ต้องเผื่อ images โมเดลหลายรุ่น ไฟล์ผู้ใช้ และ backup ตามนโยบายเก็บรักษา

สำหรับองค์กรเล็กเสนอเริ่มจากทีมเดียวและงานเดียวบนเครื่องที่ผ่าน acceptance test สำหรับองค์กรกลางเสนอแยกกลุ่มผู้ใช้และวัด concurrency ก่อนเพิ่ม capacity สำหรับองค์กรใหญ่ต้องออกแบบตัวตนและสิทธิ์ การแยกเครือข่าย การติดตามระบบ และความพร้อมใช้งานเพิ่ม ทั้งหมดเป็นแผนออกแบบที่ต้องประเมินรายลูกค้า ยังไม่มีผล load test รองรับสเปกซื้อหรือ SLA

ผล WebUI และ backend ที่อ้างอิงมาจากรอบทดสอบ 19 ตุลาคม 2026 ส่วนการเก็บ source และเวอร์ชันเป็นรอบ 20 ตุลาคม 2026 ไม่ตีความการเก็บ source ว่าทุกบริการผ่าน health test ซ้ำในวันส่งงาน การติดตั้งใหม่จากชุดส่งยังไม่ได้ตรวจ end to end บน Mac ว่าง

## การจัดการข้อมูลและสิทธิ์

key เชื่อมกับ user team และ role ที่ backend บัญชี Finance ใช้เครื่องมือค่าใช้จ่ายได้ ส่วน HR มีขอบเขตเอกสารตามสิทธิ์ Open WebUI เป็นเจ้าของ record ไฟล์ผลลัพธ์ที่ Pipe สร้าง และตรวจสิทธิ์ตอนดาวน์โหลด ผู้ดูแลระบบยังอาจเข้าถึงข้อมูลตามสิทธิ์ของแพลตฟอร์ม

ข้อจำกัดสำคัญคือชื่อบัญชี WebUI ยังไม่ผูกกับตัวตน gateway แบบครบวงจร ผู้ถือ Finance key ได้สิทธิ์ตาม key จึงต้องจัดเก็บและแจก key ให้ถูกคน การมีบัญชี Ton หรือ May เพียงอย่างเดียวไม่ใช่หลักฐานยืนยันตัวตนฝั่ง backend และการเพิกถอน key ไม่ได้เพิกถอนสำเนาไฟล์ที่เคยดาวน์โหลดหรือไฟล์ snapshot ที่แพลตฟอร์มเก็บโดยอัตโนมัติ

โมเดลและข้อมูลที่ป้อนเพื่อ inference อยู่ภายในเครื่องตาม topology ต้นแบบ แต่การติดตั้งแพ็กเกจ การดาวน์โหลดโมเดล และ Gmail OAuth หรือ Gmail API ต้องติดต่อภายนอก จึงอธิบายว่าเป็น local inference และควบคุม data flow ไม่อ้างว่าระบบทุกส่วน offline หรือไม่มีการออกเครือข่าย [2]

## แผนดำเนินงานและบริการของบริษัท

แผนต่อไปนี้เป็นข้อเสนอสำหรับการดำเนินธุรกิจ ยังไม่มีรายชื่อลูกค้าที่เซ็นสัญญา รายได้จริง หรือกำหนดส่งมอบที่ยืนยัน ส่วนตัวเลขประมาณการรายได้และงบดำเนินงานระบุใน Business Model ที่เจ้าของโครงการให้มา ระยะเวลาส่งมอบจริงต้องตกลงหลังสำรวจข้อมูลและความซับซ้อนของแต่ละองค์กร

| ระยะ | งานหลัก | ผลส่งมอบและเกณฑ์ผ่าน |
| --- | --- | --- |
| สำรวจ | สัมภาษณ์ เก็บ baseline และกำหนดเจ้าของข้อมูล | ลูกค้ายืนยันปัญหา ขอบเขต และข้อมูลที่อนุญาต |
| ออกแบบ | เลือกสถาปัตยกรรม เครื่อง โมเดล และสิทธิ์ | แบบระบบ แผนทดสอบ และต้นทุนที่ตรวจร่วมกัน |
| สร้างต้นแบบ | เชื่อมหนึ่งกระบวนงานด้วยข้อมูลสังเคราะห์ | ผลตรง expected และผ่านกรณีปฏิเสธสิทธิ์ |
| นำร่อง | ให้ทีมจำกัดใช้งาน โดยคนตรวจทุกผลสำคัญ | เปรียบเทียบเวลารวม คุณภาพ และปัญหากับ baseline |
| ส่งมอบ | ตรวจรับ อบรม ส่ง source คู่มือ และรายการเวอร์ชัน | ผู้ดูแลปฏิบัติตาม runbook และทำ recovery test ได้ |
| ดูแลและขยาย | ติดตามปัญหา ทบทวนสิทธิ์และอัปเดตในระบบทดสอบ | ขยายจำนวนผู้ใช้หลังผ่าน load test และงบที่ตกลง |

หน้าที่ที่ต้องมีคือผู้ประสานงานและวิเคราะห์กระบวนงาน วิศวกรระบบ ผู้พัฒนา integration ผู้ตรวจคุณภาพ และผู้รับผิดชอบข้อมูลของลูกค้า ช่วงเริ่มต้นบุคคลหนึ่งอาจรับหลายหน้าที่ แต่การตรวจรับข้อมูลต้องมีเจ้าของงานของลูกค้าร่วมด้วย ไม่สมมติว่า AItoB มีพนักงานครบทุกตำแหน่งแล้ว

รูปแบบบริการที่เสนอประกอบด้วยค่าประเมินและออกแบบ ค่าติดตั้งหรือปรับแต่งตามขอบเขต และค่าดูแลตามข้อตกลง อุปกรณ์และงานเชื่อมระบบเฉพาะต้องระบุแยกในใบเสนอราคา ลูกค้าเป็นผู้อนุมัติขอบเขตข้อมูลและผู้ใช้ก่อนเปิดใช้งาน

## Business Model ของ AItoB

ส่วนนี้นำข้อมูลจาก AItoB_Business_Model.txt ที่เจ้าของโครงการส่งมาเป็นแผนธุรกิจของ AItoB ตัวเลขทั้งหมดเป็นสมมติฐานและเป้าหมายสำหรับวางแผน ไม่ใช่รายได้จริง มูลค่าที่ประเมินโดยผู้ลงทุน หรือผลประกอบการที่ตรวจสอบแล้ว เจ้าของโครงการยืนยันว่าเงินเดือน Researcher และ Libero เป็นอัตราต่อคนต่อเดือน และให้ใช้เงินปันผล 30% ของกำไรตามแบบจำลอง

AItoB สร้างรายได้จากการติดตั้งระบบให้บริษัทลูกค้าและการดูแลต่อเนื่อง งานติดตั้งครอบคลุมการสำรวจความต้องการ ออกแบบ เชื่อมข้อมูลและเครื่องมือ และส่งมอบตามขอบเขตที่ตกลง บริการรายเดือนต้องกำหนดงานดูแล จำนวนผู้ใช้ ช่องทางช่วยเหลือ และขอบเขตการอัปเดตให้ชัดในข้อเสนอแต่ละราย โดยยังไม่รวมข้อตกลงหรือ SLA ที่โครงการไม่ได้กำหนด

| รายได้ตามแผน | ราคาเฉลี่ยที่ใช้คำนวณ | หน่วย |
| --- | --- | --- |
| Setup ระบบ | 300,000 บาท | ต่อบริษัทลูกค้า |
| Subscription Maintenance | 35,000 บาท | ต่อเดือนต่อบริษัทลูกค้า |

ราคาดังกล่าวเป็นค่าเฉลี่ยใน Business Model ไม่ใช่ราคาขายตายตัวสำหรับลูกค้าทุกขนาด ต้นฉบับยังไม่ได้แยกว่าราคารวมเครื่องของลูกค้า ภาษี และงานปรับแต่งส่วนใดบ้าง จึงต้องกำหนดขอบเขตต้นทุนและรายการเสนอราคาก่อนนำไปขายจริง

## โครงสร้างผู้ถือหุ้นและทีมงานตามแผน

| กลุ่มผู้ถือหุ้น | สัดส่วนรวม | รายละเอียดตามแผน |
| --- | --- | --- |
| Project and Business Lead | 51% | รับผิดชอบธุรกิจและโครงการ ยังไม่ระบุเงินเดือน |
| Technical Staff | 4% | 1 คน ถือหุ้น 4% |
| Researcher | 9% | 3 คน คนละ 3% |

| Investor | 30% | สัดส่วนที่กำหนดสำหรับผู้ลงทุน |
| รวม | 100% | เป็นโครงสร้างที่เสนอ ยังไม่ยืนยันการจัดสรรจริง |

แผนมีบุคลากรที่ระบุเงินเดือน 7 คน ได้แก่ Researcher 3 คน Libero 3 คน และ Technical Staff 1 คน ส่วน Project and Business Lead ระบุผลตอบแทนเป็นหุ้น 51% โดยไม่ได้ระบุเงินเดือนในงบนี้ ชื่อ Libero คงตามต้นฉบับและต้องกำหนดหน้าที่ให้ชัดเมื่อจัดทีมจริง บทบาทการวิเคราะห์งาน พัฒนา และตรวจรับในแผนดำเนินงานควรแจกแจงให้สอดคล้องกับทีมดังกล่าว

ก่อนใช้งบจริงต้องแจกแจงค่าใช้จ่ายแฝงและป้องกันการนับซ้ำกับ Server Maintenance รวมทั้งระบุค่าเครื่องเริ่มต้น ค่าใช้จ่ายเมื่อเพิ่มลูกค้า และรายการภาษีหรือค่าเสื่อมที่เกี่ยวข้อง งบต้นฉบับยังไม่มีรายละเอียดเหล่านี้ครบ จึงไม่ใช้ยอดงบประมาณเป็นข้อยืนยันกำไรสุทธิทางบัญชี

## เป้าหมายรายได้และผลดำเนินงานปีแรก

| รายการประมาณการ | จำนวน |
| --- | --- |
| รายได้ปีแรกตามเป้าหมาย | 5,100,000 บาท |
| งบต้นทุนปีแรก | 4,800,000 บาท |
| ผลต่างรายได้หักงบต้นทุน | 300,000 บาท |
| เป้าหมายคืนทุนตามต้นฉบับ | หลังดำเนินงานประมาณ 1 ปี |
| เป้าหมายมูลค่าบริษัทเมื่อครบปีแรก | 20,400,000 บาท |

รายได้ตามแบบจำลองคำนวณได้จาก 300,000 บาทคูณจำนวนบริษัทที่ติดตั้ง บวก 35,000 บาทคูณจำนวนเดือนลูกค้าที่ชำระค่าดูแล คำว่าเดือนลูกค้าหมายถึงลูกค้า 1 บริษัทจ่ายค่าดูแล 1 เดือน การคำนวณจึงต้องคำนึงถึงเดือนเริ่มบริการของลูกค้าแต่ละราย ไม่สมมติว่าลูกค้าใหม่ทุกรายชำระครบ 12 เดือนตั้งแต่ต้นปี

ตัวอย่างเพื่ออธิบายตัวเลขเท่านั้น หากติดตั้ง 10 บริษัท จะมีรายได้ Setup 3,000,000 บาท และถ้าเก็บค่าดูแลรวม 60 เดือนลูกค้า จะมีรายได้ค่าดูแล 2,100,000 บาท รวม 5,100,000 บาท ตัวอย่างนี้เทียบเท่าค่าดูแลเฉลี่ย 6 เดือนต่อบริษัท แต่ยังไม่ใช่ยอดขายที่มีสัญญาหรือแผนรับลูกค้ารายเดือนที่ยืนยัน

หากพิจารณาเฉพาะค่าดูแลเฉลี่ย 35,000 บาทต่อบริษัทต่อเดือน ต้องมีลูกค้าที่ชำระพร้อมกันอย่างน้อย 12 บริษัทจึงมีรายได้ 420,000 บาท ซึ่งเกินงบรายเดือน 400,000 บาท ภาพนี้ยังไม่รวมรายได้ Setup และสมมติว่างบไม่เพิ่มตามจำนวนลูกค้า จึงเป็นเพียงจุดเทียบเชิงคำนวณ ไม่ใช่จุดคุ้มทุนที่ตรวจยืนยันแล้ว

เงินที่ Investor ใส่เข้ามาต้องแยกเป็นเงินทุน ไม่บวกเป็นรายได้หรือกำไรจากการให้บริการ ตามแนวทางที่แยกกระแสเงินสดจากการจัดหาเงินออกจากการดำเนินงาน [6] ในรายงานนี้ 300,000 บาทจึงแสดงเป็นผลต่างจากรายได้ 5.1 ล้านบาทและงบต้นทุน 4.8 ล้านบาท โดยยังต้องปรับรายการที่ไม่ได้ระบุให้ครบก่อนเรียกกำไรสุทธิที่นำมาจัดสรรจริง

การคืนทุนภายใน 1 ปีและมูลค่าบริษัท 20.4 ล้านบาทคงเป็นเป้าหมายจาก Business Model ต้นฉบับ แต่ยังไม่มีจำนวนเงินลงทุนเริ่มต้น ตารางกระแสเงินสด หรือวิธีประเมินมูลค่ารองรับ จึงไม่อ้างว่าโครงการพิสูจน์การคืนทุนหรือได้รับการประเมินมูลค่าดังกล่าวแล้ว

## นโยบายจัดสรรกำไรและเงินปันผล

| Technical Staff | 4% | 3,600 บาท |
| รวม | 100% | 90,000 บาท |

ตัวเลขนี้เป็นตัวอย่างการจัดสรรตาม Business Model ไม่ใช่การรับรองว่าจะจ่ายได้เมื่อครบหนึ่งปี การใช้จริงต้องอาศัยผลดำเนินงานและจำนวนกำไรที่จัดสรรได้ในเวลานั้น โดยบันทึกเงินลงทุน เงินสำรอง และค่าใช้จ่ายที่เกี่ยวข้องแยกจากกัน

## การวัดประสิทธิภาพและต้นทุน

วัดเวลางานเดิมกับงานที่ใช้ AI ด้วยรายการชนิดเดียวกันและเกณฑ์คุณภาพเดียวกัน โดยรวมเวลาคนอ่าน ตรวจ แก้ และนำผลไปใช้ บันทึกขนาดตัวอย่าง วันที่ รุ่นโมเดล เครื่อง context และจำนวนผู้ใช้พร้อมกัน ห้ามใช้เฉพาะเวลา inference แทนเวลาทำงานทั้งหมด

ชั่วโมงที่ประหยัดต่อเดือนคำนวณจากผลต่างเวลางานเฉลี่ยต่อรายการ คูณจำนวนรายการต่อเดือน แล้วหาร 60 หากเวลามีหน่วยนาที ถ้าระบบทำให้ต้องตรวจแก้มากขึ้น ต้องรายงานผลเพิ่มเวลาได้ตามจริง ไม่เลือกเฉพาะรายการที่ดูดี

ต้นทุนรวมประกอบด้วยค่าเครื่องและการเสื่อมมูลค่า พื้นที่เก็บข้อมูล ค่าไฟ การติดตั้งและเชื่อมระบบ การดูแล อบรม backup และเวลาคนตรวจ รวมค่าบริการภายนอกเมื่อมี การใช้โมเดล local ไม่ได้แปลว่าต้นทุนเป็นศูนย์ ส่วน ROI ของลูกค้าต้องใช้ประโยชน์สุทธิและต้นทุนที่มีหลักฐานในช่วงเวลาเดียวกัน ปัจจุบันยังไม่มีผลวัดให้ใส่เปอร์เซ็นต์หรือยืนยันระยะคืนทุนของลูกค้า แยกจากเป้าหมายคืนทุนของบริษัทที่ระบุใน Business Model

## ความเสี่ยงและงานพัฒนาต่อ

ความเสี่ยงด้านคำตอบผิดหรือ prompt injection ลดด้วยการแยกข้อมูลจากคำสั่ง จำกัดเครื่องมือ ตรวจ arguments ที่ backend และมีแหล่งอ้างอิง งานการเงินใช้กฎที่ตรวจได้และให้คนรับรองผล การตรวจเหล่านี้เป็นมาตรการของต้นแบบ ไม่ใช่การรับรองว่ากันการโจมตีทุกแบบ

งานก่อนขยายใช้งานจริงได้แก่ identity binding การจัดการอายุและเพิกถอน key การทดสอบโหลด การติดตามบริการ การกำหนด data retention และ restore drill โดยต้องทดสอบการกู้คืนทั้ง source config และข้อมูลที่จำเป็นในสภาพแวดล้อมแยก ไม่ถือว่ามีไฟล์ backup แล้วเท่ากับกู้คืนได้

พัฒนาต่อในส่วนธุรกิจโดยเริ่มจาก use case ที่วัดผลได้หนึ่งงาน แล้วจึงพิจารณา document ingestion เพิ่มเติม การเชื่อมระบบบัญชี และการรองรับหลายองค์กร แต่ละส่วนต้องเพิ่มชุดทดสอบสิทธิ์และคุณภาพตามข้อมูลใหม่ ไม่ขยายความสามารถจาก metadata โมเดลโดยไม่มีการทดสอบ

## ชุดส่งงานและการทำซ้ำ

หมวด Documents มีรายงานฉบับนี้และคู่มือติดตั้งกับใช้งาน ในรูปแบบ PDF รวม 2 ไฟล์ โดยมีต้นฉบับข้อความที่แก้ไขได้รวมใน ZIP source หมวด Project Files Source Code มี ZIP รวม source 1 ไฟล์ ทุกไฟล์ต้องต่ำกว่า 100 MB ตามข้อกำหนดที่ผู้ใช้แจ้ง

ZIP รวม source ปัจจุบัน โครงสร้างติดตั้งใหม่ dependencies ที่บันทึกเวอร์ชัน config template ตัวสร้าง key ใหม่ ชุดข้อมูลสังเคราะห์ ผลทดสอบ และ checksum ไม่รวม weights โมเดล images ฐานข้อมูลผู้ใช้ อีเมลจริง token key หรือรหัสผ่าน ต้องติดตั้ง dependencies จากแหล่งทางการและสร้างข้อมูลลับใหม่บนเครื่องผู้ติดตั้ง

สคริปต์และ Dockerfile บางส่วนใน reference เป็นประวัติอ้างอิงจากระบบเดิม ชุด project มีการจัดรูปแบบเพื่อส่งมอบ เช่น ตรึง image digest และแทนอีเมลด้วย example.com การเปลี่ยนเหล่านี้บันทึกใน PACKAGING_CHANGES.json และไม่ได้แก้บริการบน Mac เดิม
