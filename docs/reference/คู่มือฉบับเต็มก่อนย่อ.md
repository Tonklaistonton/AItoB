# คู่มือติดตั้งและใช้งาน AItoB

สำหรับผู้ดูแลระบบและผู้ใช้งานต้นแบบบน Mac

ฉบับส่งงาน 20 ตุลาคม 2026 | อ้างอิง source ของ Pipe 0.1.3

## ขอบเขตคู่มือ

คู่มือนี้อธิบายการติดตั้งจาก ZIP source บนเครื่องใหม่ การกำหนดสิทธิ์รายผู้ใช้ การรับ CSV หรือ Excel การค้นเอกสารและอีเมล รวมทั้งการตรวจระบบและแก้ปัญหา ไม่ใช่ลำดับคำสั่งให้นำไปทับเครื่อง Mac ที่กำลังใช้งานอยู่ การเก็บ source รอบส่งงานไม่ได้หยุดหรือแก้บริการเดิม

เครื่องต้นแบบที่มีหลักฐานคือ Apple M5 arm64 RAM 24 GiB บน macOS 27.0.1 ใช้ Ollama 0.40.5, gemma4:12b และ Open WebUI 0.12.3 การติดตั้งใหม่จากโครงสร้างชุดส่งนี้ยังไม่ได้ตรวจ end to end บน Mac ว่าง จึงต้องทำ acceptance test ในบทตรวจระบบก่อนรับมอบ ไม่ถือว่ามี source ครบแล้วเท่ากับ clean install ผ่าน

ใช้คำสั่งในกรอบ code ตามระบบที่ระบุ บทที่เขียนว่า Mac ให้รันหลัง SSH เข้าจน prompt เป็นบัญชี Mac แล้ว ส่วนคำสั่ง Windows ให้รันในหน้าต่าง Command Prompt ฝั่ง Windows ที่ยังไม่ได้อยู่ใน SSH session

## โครงสร้างไฟล์ที่ส่งมอบ

| โฟลเดอร์ | เนื้อหาและการใช้งาน |
| --- | --- |
| project/gateway | auth, ACL, เอกสารตัวอย่าง, inference และ CSV workflow |
| project/mcp-lab และ project/gmail-lab | agent, MCP tools, Assistant, Finance API และ Gmail |
| project/webui และ project/open-webui | Pipe ล่าสุดและ Compose ของ Open WebUI |
| project/services และ tools | template บริการ ตัวสร้าง config ใหม่ และตัวตรวจ checksum |
| fixtures และ tests | ข้อมูลสังเคราะห์ expected outputs และ isolated upload tests |
| metadata และ evidence | เวอร์ชัน การปรับแพ็กเกจ และผลทดสอบ |
| reference/deployed_snapshot | source อ้างอิงจากเครื่องเดิม ไม่ใช่ลำดับติดตั้งใหม่ |

ให้ใช้ project เป็นฐานติดตั้งใหม่ ไม่ไล่รัน install_u2, install_u3, install_u4 หรือตัว patch เก่าตามลำดับ เพราะบางไฟล์มี source guards และคาดว่ามีบริการรุ่นก่อนอยู่แล้ว ประวัติใน reference มีไว้ตรวจที่มาของระบบ

## เตรียมเครื่องและซอฟต์แวร์

ต้องมี Mac แบบ Apple Silicon ที่รองรับรุ่นซอฟต์แวร์ที่เลือก Python 3.12 สำหรับการติดตั้งใหม่นี้ Docker Desktop พร้อม Docker Compose, Ollama, browser และอินเทอร์เน็ตสำหรับดาวน์โหลด dependencies กับ weights ส่วน Gmail ต้องใช้อินเทอร์เน็ตขณะทำ OAuth และเรียก Gmail API ด้วย

24 GiB เป็น RAM ของเครื่องที่ทดสอบ ไม่ใช่สเปกขั้นต่ำที่รับรองสำหรับทุกโหลด ประเมินพื้นที่สำหรับ model weights, KV cache, Docker, ไฟล์ผู้ใช้ และ backup ก่อนติดตั้ง ต้องทดสอบเครื่องจริงตาม context และจำนวนผู้ใช้ที่ต้องการก่อนจัดซื้อเพิ่ม

ติดตั้ง Ollama และ Docker Desktop จากผู้พัฒนา ตรวจเวอร์ชันก่อนเริ่ม และเปิด Docker Desktop ให้พร้อม อย่าใช้ไฟล์ binary หรือ image จากแหล่งที่ไม่ทราบที่มา แหล่งทางการอยู่ในบทเอกสารอ้างอิง

คำสั่งตรวจบน Mac:

```bash
python3 --version
docker --version
docker compose version
ollama --version
```

หากพบ ollama command not found ให้ตรวจตำแหน่งติดตั้ง เครื่องต้นแบบติดตั้งไว้ใต้บัญชีผู้ใช้ ไม่ใช่ /Applications ของระบบ:

```bash
export PATH="$HOME/Applications/Ollama.app/Contents/Resources:$HOME/.local/bin:$PATH"
export PATH="/Applications/Ollama.app/Contents/Resources:$PATH"
export PATH="/Applications/Docker.app/Contents/Resources/bin:$PATH"
export PATH="/opt/homebrew/bin:/usr/local/bin:$PATH"
command -v ollama
```

อย่าคัดลอก path ที่มีชื่อบัญชีของผู้พัฒนามาใช้ตรง ๆ เพราะชื่อ home ของแต่ละเครื่องต่างกัน

## ตรวจ ZIP และเตรียม project บนเครื่องใหม่

แตก AItoB_Project_Source.zip ไปโฟลเดอร์ทำงาน แล้วเปิด Terminal ที่โฟลเดอร์ AItoB_Source ซึ่งมี README_TH.md ก่อนติดตั้งให้ตรวจไฟล์และทดสอบ isolated upload:

```bash
python3 tools/verify_files.py
python3 -m unittest discover -s tests -v
```

ผลที่คาดหวังคือ checksum ผ่านทุกไฟล์ และ unittest ผ่าน 10 กรณี การทดสอบนี้ใช้ auth จำลอง ไม่ได้เรียกบริการจริง และไม่ยืนยันการตั้งค่า network หรือบัญชีบนเครื่องใหม่

ขั้นคัดลอก project ต่อไปนี้ใช้เฉพาะเครื่องใหม่ที่ยังไม่มี ~/aitob-lab คำสั่งจะหยุดเมื่อพบโฟลเดอร์เดิม:

```bash
if [ -e "$HOME/aitob-lab" ]; then
  echo "STOP: existing lab found"
else
  cp -R project "$HOME/aitob-lab"
fi
```

ถ้าขึ้น STOP อย่ารันขั้นสร้าง config ต่อ ให้เลือกเครื่องหรือบัญชีทดสอบแยกและวางแผนย้ายระบบก่อน คู่มือนี้ไม่สั่งลบข้อมูลเดิมเพื่อหลบเงื่อนไขดังกล่าว

## สร้าง config และ key ใหม่

จากโฟลเดอร์ AItoB_Source ให้รัน:

```bash
python3 tools/prepare_local_config.py --lab "$HOME/aitob-lab"
export LAB="$HOME/aitob-lab"
```

ตัวช่วยสร้าง keys.json, hr.key, finance.key, WEBUI_SECRET_KEY ใน .env และ services/compose.json โดยใช้ค่าลับสุ่มใหม่ในเครื่อง ไม่แสดง key บน stdout และปฏิเสธการเขียนทับไฟล์ตั้งค่าที่มีอยู่ สคริปต์นี้ไม่ได้เริ่มบริการ

| ไฟล์ในเครื่องผู้ติดตั้ง | หน้าที่ |
| --- | --- |
| gateway/credentials/keys.json | map key ไปยัง user team และ role |
| gateway/credentials/hr.key | key ของ may ใน HR และ hr_reader |
| gateway/credentials/finance.key | key ของ ton ใน Finance และ finance_reader |
| open-webui/.env | secret สำหรับ Open WebUI |
| services/.env | AITOB_LAB_ROOT สำหรับแก้ path ของ bind mounts |
| services/compose.json | config ที่ได้จาก template ไม่มี key จากเครื่องเดิม |

เก็บไฟล์เหล่านี้เฉพาะเครื่องผู้ดูแล ไม่อัปโหลดลง Forms หรือ Git และไม่วาง key ในข้อความแชต ให้ผู้ดูแลส่งมอบ key ตามช่องทางภายในที่ตกลงและตั้ง User Valves ของบัญชีที่ถูกต้อง ผู้ถือ key ได้สิทธิ์ตาม key แม้ชื่อบัญชี WebUI จะต่างกัน

## เตรียม Ollama และโมเดล

ถ้า Ollama App เปิดบริการอยู่แล้วไม่ต้องเริ่ม serve ซ้ำ ถ้ายังไม่มี server ให้เปิด Terminal แยกแล้วรัน ollama serve จากนั้นใช้ Terminal อีกหน้าต่างดึงและตรวจโมเดล:

```bash
ollama pull gemma4:12b
ollama list
ollama show gemma4:12b --verbose
```

เครื่องเดิมรายงาน 12.4B parameters, MLX, nvfp4, safetensors และขนาดที่แสดง 7.7 GB ขณะที่ tag สามารถเปลี่ยนรุ่นย่อยตามเวลาและแพลตฟอร์มได้ ให้บันทึก Ollama version, model ID และ metadata ของเครื่องใหม่ แล้วทดสอบก่อนเทียบผล ไม่ถือว่าใช้ชื่อ tag เดียวแล้ว bytes จะเหมือนกันเสมอ

source ใช้ MODEL เป็น gemma4:12b ที่ Gateway และเรียก http://127.0.0.1:11434/api/chat หลายเส้นทางกำหนด num_ctx 4096 แม้โมเดลรายงานรองรับ context สูงสุด 262144 tokens ไม่ปรับเพิ่มจนกว่าจะวัด RAM และเวลาใหม่

## สร้าง images และเปิดบริการ

บน Mac ให้ตั้ง LAB ใน Terminal ที่จะใช้คำสั่งต่อไปนี้ หากกลับเข้ามาใหม่ต้องตั้งตัวแปรอีกครั้ง:

```bash
export LAB="$HOME/aitob-lab"
docker build -t aitob-mcp-lab:day2 "$LAB/mcp-lab"
docker build -t aitob-gmail-lab:day2 "$LAB/gmail-lab"
```

Dockerfile สำหรับชุดส่งตรึง Python 3.12.15 และใช้ requirements.snapshot.txt จาก image เดิม ได้แก่ MCP 2.3.0 กับแพ็กเกจ Google API ตาม metadata ที่แนบ เวอร์ชันถูกบันทึกแต่ยังไม่ได้ตรึง wheel hashes และยังไม่ได้ rebuild บน Mac ว่าง หาก registry ไม่มีรุ่นนั้นให้บันทึกปัญหาและทดสอบการเปลี่ยน dependencies ในสภาพแวดล้อมแยก ไม่อัปเกรดเงียบ ๆ แล้วอ้างผลเดิม

เปิด Gateway ใน Terminal แยกและคงหน้าต่างไว้ระหว่างตรวจรับ:

```bash
cd "$HOME/aitob-lab/gateway"
python3 -u gateway.py
```

เปิด Gmail และ Assistant จาก Terminal อีกหน้าต่าง:

```bash
export LAB="$HOME/aitob-lab"
docker compose --env-file "$LAB/services/.env" \
  -f "$LAB/services/compose.json" config --quiet
docker compose --env-file "$LAB/services/.env" \
  -f "$LAB/services/compose.json" up -d
docker compose -f "$LAB/open-webui/compose.yaml" up -d
```

Open WebUI ใช้ image digest ที่เก็บจากรุ่น 0.12.3 เพื่อไม่อาศัย tag main ที่เปลี่ยนได้ Gmail service เริ่มรับคำขอได้ก่อนตั้ง OAuth แต่การเรียกอีเมลจะยังไม่สำเร็จจนกว่าจะตั้งบัญชีเจ้าของและ token ครบ

พอร์ต host ของบริการใน Compose ผูกกับ 127.0.0.1 ส่วนบริการใน container รับที่ 0.0.0.0 ภายใน container ตาม source อย่าเปลี่ยนพอร์ต host เป็น 0.0.0.0 เพื่อแก้ปัญหาเชื่อมต่อ เพราะจะเปลี่ยนขอบเขตการเข้าถึง การเชื่อมจาก container ใช้ host.docker.internal ตามต้นแบบ Docker Desktop และต้องตรวจจริงบนเครื่องใหม่

## ติดตั้ง Pipe และตั้งบัญชีผู้ใช้

เปิด http://127.0.0.1:3000 บน Mac สร้างบัญชีผู้ดูแลของเครื่องใหม่ตามขั้นตอน Open WebUI จากนั้นเข้า Admin Panel และ Functions สร้าง Function โดยใช้โค้ดทั้งหมดจาก project/webui/aitob_openwebui_pipe.py บันทึกและเปิดใช้งาน ตรวจว่า header แสดง version 0.1.3

กำหนด Valves ของ Function ให้ BASE_URL เป็น http://host.docker.internal:8002 ตาม topology นี้ สร้างบัญชีผู้ใช้แยกสำหรับ Ton Finance และ May HR ตามวิธีจัดการบัญชีของแพลตฟอร์ม แล้วในแต่ละบัญชีเลือก AItoB Assistant และตั้ง AITOB_API_KEY ใน User Valves โดยใช้ key ของบุคคลนั้นเท่านั้น

ไม่ตั้ง Finance key เป็นค่า global เพื่อให้ทุกบัญชีใช้ร่วมกัน หลังตั้งค่าควรทดสอบสลับบัญชีจริง เพราะ role ที่ WebUI แสดงกับ role ที่ gateway รับจาก key ยังไม่ใช่ identity binding เดียวกัน

## เข้าใช้งานจาก Windows ผ่าน SSH

ต้องเชื่อม SSH ไป Mac ได้ก่อน ผู้ดูแล Mac ต้องเปิด Remote Login และอนุญาตบัญชีที่กำหนด ตรวจเครือข่ายและ host ปัจจุบันกับผู้ดูแล ไม่ถือว่า IP ของเครื่องพัฒนาใช้ได้กับเครื่องใหม่เสมอ

รันใน Command Prompt ฝั่ง Windows โดยแทน mac-user และ mac-host ด้วยค่าของผู้ติดตั้ง:

```cmd
ssh -N -L 3001:127.0.0.1:3000 mac-user@mac-host
```

ใส่รหัสผ่านหรือใช้ key ตามที่องค์กรตั้งไว้ เปิดหน้าต่างนี้ค้างไว้ แล้วเปิด http://127.0.0.1:3001 ใน browser ของ Windows หากปิด SSH หรือเครื่องพักการเชื่อมต่อ ช่องทางนี้จะใช้ไม่ได้ แม้เว็บบน Mac ยังทำงานอยู่

## ใช้งานไฟล์ค่าใช้จ่าย

เข้า Ton Finance เปิด New Chat และเลือก AItoB Assistant กดแนบไฟล์ เลือก CSV หรือ Excel หนึ่งไฟล์ รอให้อัปโหลดเสร็จ แล้วส่งคำสั่ง ตรวจไฟล์ค่าใช้จ่าย ระบบจะตรวจสิทธิ์และตอบสรุปจำนวนแถว ยอดเงิน กราฟสัดส่วน พร้อมลิงก์ดาวน์โหลด CSV ที่สะอาดแล้วและเหตุผลรายแถว

ใช้ fixtures/AItoB_ค่าใช้จ่ายสังเคราะห์.xlsx สำหรับตรวจรับ ผลที่คาดหวังคือก่อนตรวจ 6 แถว ผ่าน 3 ซ้ำ 1 ปฏิเสธ 2 ยอด 2000.00 บาท cleaned CSV มี EXP001 1200.00, EXP002 300.00 และ EXP005 500.00 รายงาน audit ระบุสถานะของแถวต้นทาง 2 ถึง 7

| ข้อกำหนดไฟล์แนบ | ขอบเขตปัจจุบัน |
| --- | --- |
| คอลัมน์ตามลำดับ | expense_id,vendor,amount |
| CSV | UTF 8 หรือ UTF 8 BOM |
| Excel | .xlsx หนึ่งชีต ใช้คอลัมน์ A ถึง C |
| ขนาดไฟล์ดิบ | ไม่เกิน 1,000,000 bytes |
| แถวข้อมูล | ไม่เกิน 1,000 แถว ข้ามแถวว่างทั้งหมด |
| ยอดเงิน | THB เป็นบวก ไม่เกิน 1,000,000,000 บาท ทศนิยมไม่เกิน 2 ตำแหน่ง |
| รูปแบบไม่รองรับ | สูตร merged cells macros external links และหลายชีต |

การตรวจตัดช่องว่าง ตรวจยอดด้วย Decimal แยกรายการรหัสซ้ำที่ข้อมูลเหมือนกันออก และปฏิเสธรหัสซ้ำข้อมูลขัดกันหรือข้อความที่เสี่ยงเป็นสูตรในช่องที่กำหนด กราฟเปรียบเทียบจำนวนแถว ไม่ใช่เปอร์เซ็นต์ลดเวลา และไฟล์แนบไม่เขียนทับ CSV เดโมเดิม

อีกเส้นทางหนึ่งคือส่งคำสั่ง ช่วยทำความสะอาด CSV ค่าใช้จ่าย แล้วสรุปยอดรวม โดยไม่แนบไฟล์ Agent จะใช้ CSV คงที่ใต้ gateway/data/finance/expenses.csv ตามสิทธิ์ และเขียน gateway/runtime/finance/expenses_cleaned.csv การพิมพ์ ดาวน์โหลด CSV หรือ /download ส่งออกผลคงที่นี้ ไม่ใช่คำสั่งเลือกผลไฟล์แนบเก่า ให้ดาวน์โหลดผลไฟล์แนบจากลิงก์ในคำตอบของรายการนั้น

## ใช้งานเอกสารองค์กร

ตัวอย่างสำหรับ May HR คือ บริษัทให้วันลาพักร้อนกี่วัน และต้องแจ้งล่วงหน้ากี่วัน ระบบค้นเอกสารที่มีสิทธิ์แล้วตอบพร้อม source hr-leave เอกสารสมมติระบุ 12 วันต่อปีและแจ้งล่วงหน้า 3 วัน บัญชี Finance มีเอกสารตัวอย่างตามสิทธิ์ของตน

เอกสารปัจจุบันอยู่ใน gateway/documents.py และชุด keyword อยู่ใน search.py การเพิ่มเอกสารต้องแก้ source พร้อม ACL และทดสอบสิทธิ์ก่อนใช้งาน ยังไม่มีหน้าจอนำเข้าคลังเอกสารทั่วไปหรือ vector database ในชุดนี้ หากไม่พบเอกสารที่ตอบได้ ควรตอบว่าไม่พบในเอกสารที่เข้าถึงได้

## ตั้งค่า Gmail เมื่อเลือกใช้ส่วนอีเมล

ส่วนอีเมลเป็นบริการเสริม ต้องใช้บัญชีที่เจ้าของอนุญาตและ Google OAuth ใหม่ ชุดส่งไม่มี client_secret.json หรือ token.json อีเมลใน email_access.py ถูกแทนด้วย mailbox-owner-1@example.com เพื่อส่งงาน ผู้ติดตั้งต้องเปลี่ยน EXPECTED_EMAIL เป็นบัญชีที่อนุญาตและตรวจว่า OWNER_USER ตรง identity ที่กำหนด ค่าเริ่มต้นของโครงการคือ ton

ผู้ดูแลเตรียม Google Cloud project เปิด Gmail API และสร้าง OAuth client แบบ Desktop app ตามเอกสาร Google [4] ดาวน์โหลด client_secret.json ลง gmail-lab/credentials เฉพาะในเครื่อง จำกัดสิทธิ์ไฟล์ และเรียกตัวช่วย authorize โดยเผยพอร์ต callback เฉพาะ localhost:

```bash
export LAB="$HOME/aitob-lab"
docker run --rm -it -p 127.0.0.1:8765:8765 \
  -v "$LAB/gmail-lab:/app" -w /app \
  aitob-gmail-lab:day2 python authorize_gmail.py
```

เปิดลิงก์ที่โปรแกรมแสดงใน browser บน Mac และให้เจ้าของบัญชีทำขั้นตอนยืนยันด้วยตนเอง หากใช้ browser ฝั่ง Windows ให้เปิด SSH tunnel ของพอร์ต 8765 เพิ่มก่อนทำ OAuth และอย่าส่ง URL ยืนยันที่มี state หรือ code ให้ผู้อื่น token จะถูกบันทึกในเครื่อง ไม่แนบลงรายงานหรือ source

OAuth scope ใน source คือ gmail.readonly ซึ่งเป็นสิทธิ์อ่าน Gmail ของบัญชี ไม่ได้จำกัดเฉพาะ label ด้วย OAuth โค้ดของโครงการจึงตรวจเจ้าของ mailbox และกรอง label AItoB-Demo อีกชั้น ผู้ติดตั้งต้องสร้าง label นี้และใส่เฉพาะอีเมลตัวอย่างที่อนุญาต ไม่ใช้ mailbox จริงของผู้อื่นทดสอบ

หลังตั้งครบ ใช้บัญชีผู้เป็นเจ้าของ key แล้วส่งคำสั่ง เช่น ค้นหาอีเมลใน AItoB-Demo เรื่องประชุม 1 ฉบับ อ่านแล้วสรุป ระบบค้นก่อนอ่านและใช้รหัสที่ได้จากการค้นในคำขอเดียวกัน ตัว agent จำกัด tool calls 4 ครั้งและการอ่าน 2 ฉบับต่อคำขอ ส่วนข้อความส่งให้โมเดลถูกตัดตามเพดานใน source ต้องตรวจสถานะ truncated ก่อนอ้างว่าอ่านครบ

## ตรวจระบบและตรวจรับหลังติดตั้ง

ตรวจ health ของ Gateway และ Assistant บน Mac ก่อนตรวจผ่าน WebUI:

```bash
curl --fail http://127.0.0.1:8000/health
curl --fail http://127.0.0.1:8002/health
docker compose --env-file "$HOME/aitob-lab/services/.env" \
  -f "$HOME/aitob-lab/services/compose.json" ps
docker compose -f "$HOME/aitob-lab/open-webui/compose.yaml" ps
```

จากนั้นทดสอบตามตารางและบันทึกผลใหม่ของเครื่องติดตั้ง อย่าใช้หลักฐานเก่าแทนผลตรวจเครื่องใหม่:

| ขั้นตรวจ | เกณฑ์ที่ต้องได้ |
| --- | --- |
| ไม่ส่ง key หรือส่ง key ผิด | API ที่ตรวจสิทธิ์ปฏิเสธด้วย 401 |
| Finance ส่ง fixture XLSX | ได้ 6 แถว ผ่าน 3 ซ้ำ 1 ปฏิเสธ 2 ยอด 2,000.00 บาท |
| ดาวน์โหลดผล | เนื้อหา CSV และ audit ตรง expected และ hash ของ input ตรง fixture |
| HR สั่งตรวจค่าใช้จ่าย | ถูกปฏิเสธ ไม่แสดงลิงก์ผลใหม่ของ Finance |
| HR เปิด URL ผล Finance | ไม่ส่งเนื้อหาไฟล์ของ Ton ให้ |
| ผู้ใช้ส่ง role Finance ใน request | ไม่ยกระดับสิทธิ์จากข้อมูล client |
| เอกสาร HR | คำตอบตรงเอกสารตัวอย่างและมี source |
| Gmail เมื่อเปิดใช้ | ตรวจเจ้าของตรง อ่านได้เฉพาะขอบเขตแอป และปฏิเสธผู้ใช้คนอื่น |

## การเริ่มงานประจำวันและการดูแล

ตรวจว่าเครื่องตื่น เครือข่ายพร้อม Ollama และ Docker Desktop เปิดแล้ว ตรวจ Gateway และ Compose services ตามบทก่อนหน้า หากใช้ Gateway แบบรันใน Terminal ต้องคงหน้าต่างนั้นไว้ เครื่องเดิมมี LaunchAgents สำหรับ Ollama กับ Gateway แต่ไฟล์ใน reference มี path ตามบัญชีเดิม จึงต้องสร้างให้ตรงเครื่องและตรวจการเริ่มหลัง login ก่อนใช้งานจริง

เก็บ source version และ config template แยกจาก backup ข้อมูลลับ สำรอง keys, OAuth, Open WebUI data และไฟล์ที่ต้องรักษาในพื้นที่ควบคุมสิทธิ์หรือเข้ารหัสตามนโยบายขององค์กร การสำรองฐานข้อมูลควรใช้วิธีที่ได้ snapshot สอดคล้องกัน ไม่คัดลอกไฟล์ SQLite ขณะเขียนโดยไม่จัดการ WAL และไม่ส่ง backup เหล่านี้ให้อาจารย์แทน source

ก่อนอัปเดตให้เก็บรุ่นเดิม ทดลองในระบบแยก รันทดสอบ และกำหนดวิธีย้อนกลับ ทดสอบ restore บนสภาพแวดล้อมแยกก่อนอ้างว่ากู้คืนได้ครบ ปัจจุบันไม่มีหลักฐาน restore drill หรือ SLA ระยะเวลาฟื้นระบบ

## การแก้ปัญหาที่พบบ่อย

| อาการ | สิ่งที่ควรตรวจ |
| --- | --- |
| Windows เปิด 127.0.0.1:3001 ไม่ได้ | SSH tunnel ยังเปิดอยู่หรือไม่ และเว็บ Mac พอร์ต 3000 ทำงานหรือไม่ |
| SSH Connection refused | host หรือพอร์ตถูกต้อง Remote Login เปิด และบัญชีได้รับอนุญาตหรือไม่ |
| SSH timeout | เครือข่าย เส้นทาง VPN และสถานะเครื่อง โดยไม่สรุปว่า password ผิด |
| docker command not found | PATH และตำแหน่ง Docker.app ใน session SSH |
| Cannot connect to Docker daemon | เปิด Docker Desktop และรอ daemon พร้อม |
| ollama command not found | PATH ของ user Applications หรือ .local/bin ต่างจาก shell เดิม |
| 401 หรือไม่มี key | ตั้ง User Valves ด้วย key ของบัญชีนั้น ตรวจว่าไม่มีช่องว่างเกิน |
| 403 | ตรวจสิทธิ์จาก keys.json ไม่ใช้ prompt เปลี่ยน role หรือแจก Finance key รวม |
| 502 หรือ timeout | ตรวจ Gateway Ollama Gmail และ host.docker.internal ตามเส้นทางที่มีปัญหา |
| Gmail connected mailbox mismatch | EXPECTED_EMAIL กับ OAuth profile ไม่ตรง หยุดและให้เจ้าของตรวจ |
| ไฟล์ 413 หรือ 422 | ตรวจขนาด schema สูตร จำนวนชีต จำนวนแถว และรูปแบบยอดเงิน |
| แนบไฟล์แล้วไม่เข้าเส้นทางตรวจ | ตรวจ Pipe 0.1.3 และใช้คำสั่ง ตรวจไฟล์ค่าใช้จ่าย อย่างชัดเจน |
| ใช้ไฟล์ติดตั้งเก่าแล้ว STOP | source guard ป้องกันการเขียนทับ อย่าปิด guard เพื่อฝืนติดตั้ง |

บันทึกเฉพาะรหัสสถานะ ชื่อบริการ รุ่น และขั้นตอนที่ทำซ้ำได้ ไม่ส่ง raw log ที่มี headers key เนื้อหาอีเมล หรือข้อมูลการเงินจริงให้ผู้อื่น
